# サングラスくま株式会社 2.0 基本設計（2026-11-15）

社長の決定（2026-11-15）を新しい基本設計とする。過去の細かな仕様・追加指示のうち、この設計と矛盾するものは廃止する。
動作を確かめてきた接続（楽天API・OpenAI・画像生成・鍵と環境変数・予算と費用の記録・定期実行）は再利用する。

## 1. 体験
「自分のiPhoneの中に、小さなAI会社を持っている」。見下ろし型のドット絵オフィスで、7人のAI社員が **実際の仕事の記録どおりに** 動く。
働いていない社員は待機として見える。働いているふりの演出はしない。

## 2. 評価
社員の人数・実行回数・テスト件数ではなく、**完成した投稿セット（商品・URL・紹介文・画像がそろったもの）と、社長の採用・売上** で評価する。

## 3. 社員（7人）と仕事
| 社員 | 仕事 | 中身（再利用する処理） |
|---|---|---|
| バイヤー | 主役の商品を探す／残りの商品をそろえる | 楽天の商品検索（lib/rakuten.js）＋AIが1点選ぶ（誰に・悩み・なぜ今）／gatherSlots・pickProducts（lib/postset.js） |
| 監査 | 商品・文章・画像を確かめる | 楽天で引き直し（lookupItem）／codeCheck・監査AI（lib/production.js）／画像の品質確認（lib/kuma-cover.js） |
| 企画 | 投稿の構成を決める | planSet（lib/postset.js 経由の planStep） |
| ライター | キャプション・商品カード・ROOM紹介文 | copyStep・roomStep（lib/production.js） |
| 編集 | 監査や社長の指摘で直す | editStep・applyEdit・事実だけのROOM紹介文（lib/production.js） |
| デザイナー | サングラスくまが商品を使う表紙画像 | sceneStep・imageStep（lib/kuma-cover.js・正式マスター） |
| 広報 | 完成品に仕上げて社長に届ける | キャプションの組み立て（lib/instagram.js）・PR表記の確認（コード） |

将来の事業（note出版・デジタル商品）は、同じ社員が別の「仕事の型（工程の並び）」を担当する形で足す（社員と記録の仕組みは共通）。

## 4. 仕事の流れ（1件の投稿セット）
```
バイヤー：主役の商品を探す → 監査：商品を確かめる → 企画：構成を決める → バイヤー：残りの商品をそろえる
→ ライター：文章を書く → ライター：ROOM紹介文 → 監査：文章を確かめる（不足なら 編集：直す → 監査 を最大2回）
→ デザイナー：場面を決める → デザイナー：画像を作る → 監査：画像を確かめる → 広報：仕上げて社長に届ける
```
- 定期実行のたびに、時間（約25秒）の許す限り工程を続けて進める（画像を描く工程は次の回の最初。1回の実行は60秒以内）。引き継がれた社員は「担当中」と表示する。工程ごとに「開始・完成・引き継ぎ・止まった理由」を記録（出来事の記録）し、画面はこの記録だけから作る
- 社長の確認待ちがあっても、次の投稿セットを作り続ける（確認待ちが5件になったら（2026-11-16 に3件から変更・15章）、見られない物に費用をかけないため新しくは作らない）
- 社長の修正依頼は、編集→監査→広報の短い流れで直して届け直す（ほかの仕事より先に）
- 画像の予算（1日1枚・月200円）を使い切ったら、その投稿セットは「画像待ち」にして、翌日デザイナーが続きから作る。待っている間もほかの仕事は進む（画像待ちが2件になったら、文章だけ作ってもたまるので新しくは作らない）
- 止まった工程は2回までやり直し、それでも駄目なら理由を平易に記録して次の仕事へ移る

## 5. 社長の画面（/v2/）
タブは4つだけ：オフィス／完成品／対応／お金。
- オフィス：ドット絵のオフィス（社員をタップ → 今の仕事・直近の成果）、今日の仕事の流れ（時刻・社員・何をしたか・誰へ引き継いだか・止まった理由）
- 完成品：商品・商品URL・紹介文（Instagram・ROOM）・画像（AI生成イメージと表記）。採用・却下・修正依頼。投稿は社長が手で行う（自動投稿しない）
- 対応：社長にしかできないこと（確認待ちの完成品、切り替え）
- お金：今日・今月のAIの費用（実測）と、売上（楽天にAPIが無いため社長の手入力）
- 出さないもの：監査の点数・採点理由・長い技術ログ・設定。必要な技術情報は開発者向けの記録（記録の dev 欄・サーバーの保存場所）に残す

## 6. 保存（Upstash Redis・名前の頭に v2:）
v2:job（今の仕事）／v2:events（出来事の記録・新しい順・400件）／v2:sets・v2:set:<id>（完成品）／v2:imagewait（画像待ち）／v2:fixq（社長の修正依頼）／v2:used（使った商品）／v2:sales（売上の手入力）／v2:active（2.0に切り替え済みか）
- 画像は今までと同じ保存場所（kuma:media）と /api/media で配信
- 予算・費用の記録は今までと同じもの（lib/budget.js）を使う（1.0と2.0で上限を共有。増額しない）
- 二重実行の防止は、1.0と同じ鍵（worker:lock）を使う（同時に動かない）

## 7. 切り替え（旧アプリを壊さない）
- 2.0は同じアプリの /v2/ に置く。1.0の画面・データ・定期実行には触らない
- 定期実行（QStash → /api/worker）は、v2:active が '1' のとき2.0だけを動かす。切り替えの前（動作確認中）は1.0と2.0で交互に使う（2.0も実際に働き、オフィスで見える）
- 切り替えは2.0の「対応」タブのボタン（社長の操作）。戻すボタンもある（元に戻せる）
- 切り替えの前に、旧データのバックアップ（1.0の「社長の対応」→ バックアップを保存）を社長にお願いする。旧データは消さない
- 動作確認のため、手動の実行（GitHub Actions の worker・target=v2）で2.0だけを動かせる

## 8. 再利用するもの／廃止するもの
再利用：lib/rakuten.js・lib/ai.js（runWithModels・鍵の伏せ字）・lib/ai-usage.js・lib/budget.js・lib/kv.js・lib/qstash.js・lib/postset.js（planSet・gatherSlots・pickProducts・qualityCheck）・lib/production.js（各工程・codeCheck・事実だけの文章）・lib/agents.js（判定 decide）・lib/kuma-cover.js・lib/kuma-master*.js・lib/instagram.js・server/media.js・api/[route].js

2.0では使わない（1.0には残す。消さない）：バイヤーの発掘の切り口・購入動機の比較・候補の在庫と再審査・営業交流AI・棚（公開待ち3＋控え6）・同期（端末とサーバーの写し）・経営会議・プレゼン/広げる/商品ドロボー/検索ジョブ等の旧画面・点数の表示

## 9. 守ること（変えない）
確認できない情報を作らない／体験の表現・誇張・医療の効果を書かない／PR表記／AI生成画像は「AI生成イメージ」と表記／楽天ROOM・Instagramへの投稿とコメントは自動化しない／秘密の鍵は環境変数だけ（画面・記録に出さない）／予算（月1,000円・自律運営1日25円・画像 月200円・1日1枚）を増やさない

## 10. 24時間の自律運営（社長の決定 2026-11-16・この章が4〜7章より優先）
- 社長の指示は不要：定期実行のたびに、上限に空きがあれば企画が新しい案件を自分で始める（季節・行事・これまでの完成品・社長の採用/却下から提案）。似た企画（最近20件と似たテーマ・同じ検索語・却下した企画）はプログラムで弾いて考え直す（重複率として数える）。社長がテーマや楽天の商品URLを指定したら、次の新しい案件で優先する
- 工程：企画（提案）→バイヤー（主役の商品：定番・新商品・予約・季節・ギフトの方向で検索）→監査（楽天で再確認）→企画（構成）→バイヤー（残りの商品）→ライター（Instagram・ROOM）→監査（文章）→編集（差し戻しの修正・最大2回）→編集（全体の整合性）→デザイナー（場面・画像）→監査（画像）→広報（ハッシュタグ・投稿順・本命と代替の比較・注意事項）→納品
- 差し戻し：監査→編集（2回）、監査→バイヤー（商品が買えない・2回）、バイヤー→企画（商品が見つからない・2回）、画像の描き直し（日をまたいで3回）。上限を超えたら理由を残して止め、次の案件へ
- 並行：案件は進行中と画像待ちを合わせて最大3件（画像は1日1枚のため、それ以上先に文章を作っても納品まで何日もたまるだけ。2026-11-16 本番の確認で変更）。各社員は1回の定期実行で2工程まで。画像（時間がかかる）は回の最初に
- 再開：失敗は15分×回数の間隔で再試行（3回まで）。予算待ち・画像待ちは、予算が戻った回に続きから。1回の実行は約25秒で区切り、途中経過は案件（v2:cases）に保存
- 社員の状態：仕事中／担当中／引き継ぎ中（10分以内に次の部署へ渡した）／エラー（再試行待ち）／予算待ち／画像待ち／待機。すべて実際の案件と記録から決める
- 納品：テーマと狙い・商品（本命/代替・商品画像・正確な名前・価格・URL・確認状況。未確認は「未確認」と明示）・比較・表紙画像（AI生成イメージ）・キャプション・ROOM紹介文・ハッシュタグ・注意事項・推奨の投稿順。画面のお知らせ・タブの数字で知らせる（スマホへのプッシュ通知は未実装：鍵の設定が必要）
- 成果：完成数・投稿できる品質に届いた割合（完成／（完成＋停止））・商品情報を楽天で確認できた割合・企画の重複率・1セットあたりの制作費・採用数・投稿数・売上（手入力）。閲覧・クリックは公式APIの鍵が無いため未取得
- 上限：画像が1日1枚のため、完成品は最大で1日1件（増やすには社長の判断が必要。画像の月200円の範囲で1日2枚まで設定できる）

## 11. 予算の運用と商品選定（社長の決定 2026-11-16）
- 上限は維持：AI全体の月1,000円・自律運営の1日25円・画像の月200円（社長の2つ目の指示に合わせ、厳しい方を採用。1つ目の指示の「1日25円・画像月200円の一時撤廃」は行っていない）
- 画像の「1日1枚」の固定制限は撤廃：月200円の範囲で、枚数とタイミングはAI社員が判断。月初に使い切らないよう、1日の目安＝画像の月の残り÷月末までの日数×3。全体の月の予算のうち100円は画像に使わず、ほかの工程に残す。生成前に見込み（20円）で確かめ、実費を記録
- 14日間の試験運用：最初の定期実行で開始時点の今月の支出を記録し、それ以降の増分を数える。期間中の合計1,000円に届く有料の処理はしない。使える残り＝試験の残りと今月の残りの少ない方（二重に数えない）。期間後も上限は自動で増やさない
- 画像以外ができた案件は「画像待ちの制作物」として完成品タブで見られる。画像ができたら正式な投稿セットとして納品
- 商品選定：(A) 高級感があり価格に見合う価値（基本3万円以内）と (B) 高級品に迫る高コスパを重視。価格帯の目安（3,000円未満／〜1万円／〜2万円／〜3万円）は探す目安で、構成のルールではない。選定理由は1〜2行。「高級品と同等」などの確認できない断定は、選定理由から外し、文章にあれば編集で直す
- 場面の根拠：使い方の文と商品データに共通する5文字以上の言葉があれば根拠にする（AIの書いた根拠の言葉そのものは信用しない）

## 12. 試験運用中の予算（社長の決定 2026-11-16・11章の上限より優先）
- 14日間の試験運用中は、1日25円・画像の1日の目安・画像の月200円・ほかの工程に残す100円を使わない。止めるのは「試験期間中の合計1,000円」と「今月の合計1,000円」だけ（二重に数えない）
- 上限に届く有料の処理はしない。期間が終われば通常の上限（11章）に戻る。自動で増やさない
- 1.0（交互の定期実行）は通常の上限のまま

## 13. 完成品ページの投稿の準備（社長の依頼 2026-11-16「1.0の時みたいに」）
- Instagramに貼る画像：1.0と同じ部品（js/ig-render.js・ig-covers.js・ig-multi.js・carousel-layout.js）を、この端末で描く（AIなし・0円）。表紙（サングラスくまのAI画像＋タイトル・「AI生成イメージ」の表記）→ 商品カード（楽天の商品写真・価格・短い名前）→ 楽天ROOMへの案内。まとめて写真に保存できる
- 楽天ROOMの登録：商品ごとに「紹介文（＋ハッシュタグ）をコピーしてROOMの登録画面を開く」→ 社長が貼り付けて登録 →「ROOMに登録した」で記録（社長の申告・取り消し可）。ROOMへの投稿は自動化しない

## 14. ポスト（社長の依頼 2026-11-16）
- 社長が「ただ調べてほしい」スクショ（Instagram・ストーリーズ・YouTube・テレビなど）を「ポスト」タブに入れると、その場で調べる（lib/v2/post.js）
- 鑑定（新しい社員）：画像を読むAI 1回で、身につけている物・使っている物の候補を抜き出す。人物は画像から判断しない（社長のメモだけ）。ブランドはロゴ・文字がはっきり読めるときだけ
- バイヤー：候補ごとに楽天で探す。判定はコード：型番の文字が一致＝同一商品確認済み／文字が一致＝同一商品の可能性あり／見た目だけ＝類似商品／見つからない＝未特定
- 投稿セットは作らない。スクショは調べるためだけに使い、推測できないIDで非公開に保存（社長が消せる）。1日30枚まで・費用は月1,000円・試験運用の合計の中で数える

## 15. 並行処理・仕事探し・広報の常設（社長の依頼 2026-11-16・この章が10章の「並行」「社員の状態」より優先）
- 実装前の制約の確認：(1) 定期実行は QStash の15分ごと（無料枠）で、切り替え前は1.0と交互＝2.0は30分に1回 (2) 1回の実行は関数の上限60秒・二重実行の鍵58秒・工程を始めるのは25秒まで (3) 以前は1回の実行の中で工程を1つずつ順番に進めていた（同時には1つ）(4) 新しい案件は「進行中＋画像待ちで3件」に達すると始めなかった（画像待ちの案件が、次の案件を止めていた）(5) 楽天は1秒1回（同じ検索の中だけで守っていた）(6) AIの費用の記録は1つのリクエストで1つの箱（同時に進めると、どの工程の費用か取り違える）
- 並行：1回の実行の中で、3本の「レーン」が違う案件の工程を同時に進める（MAX_PARALLEL=3）。同じ案件は同時に2つのレーンで進めない（工程の順番と監査はそのまま）。1人の社員は同時に1つの仕事だけ・1回の実行で3件まで（AGENT_PER_TICK）。工程が終わると、空いたレーンがすぐ次の工程を取る（引き継ぎ先の社員が空いていれば、同じ回の中で続く）
- 予算：同時に進めている工程の費用の見込みを足してから確かめる（同時に始めて上限を超えない）。月1,000円・試験運用の合計1,000円は変えない
- 楽天：同じサーバーの中の呼び出しすべてで1.1秒の間隔をあける（lib/rakuten.js の paceGate）。AIの費用は工程ごとに別の箱で記録する（lib/ai-usage.js の isolated）
- 案件の上限：進行中は3件まで（画像待ちは数えない。画像待ちは2件まで）。社長の確認待ちが5件になったら新しくは始めない（3件から変更）。新しい案件は1回の実行で1件まで（量産しない）
- 定期実行：1.0の番でも、1.0に仕事が無くすぐ終わったとき（6秒以内）は、同じ回で2.0を進める（空回りしない）
- 仕事探し：案件の工程が無い社員は、自分の担当で本当に必要な仕事だけを探す。監査＝広報のコメント案の採点／納品から24時間たった完成品の商品を楽天で確かめ直す（価格の変化・販売終了を社長に知らせる。AIは使わない）。広報＝Instagramの交流（下）。企画＝空きがあれば新しい案件。ほかの社員は、担当の工程が来るまで「仕事なし」とその理由を表示する（仕事をしているように見せる処理はしない）
- 広報の交流（lib/v2/pr.js）：交流候補（投稿の文章を確認できた投稿＝社長が追加／Facebookログイン方式の公式APIで取得）にコメント案 → 監査が採点（別のAI呼び出し・コードの確認つき）→ 直す（2回まで）→ 合格だけ社長の承認待ち。承認 → 社長がInstagramで自分で送り「送った／送れなかった」を記録（社長の申告。pr:comment:log にも残す）。決まり：1日3件まで・同じアカウントに7日に1件・1つの投稿に1件・失敗は2回で見送り。関連アカウントは公式サイトがリンクしているInstagram（7日ごと・0円）
- できないこと（実装済みと言わない）：コメント・いいね・フォローの送信（公式APIに無い・非公式な自動操作はしない）／公式APIが未設定の間は投稿を自動で集められない／ハッシュタグ検索はMetaの審査後
- 社員の状態：担当中（今この瞬間に処理している。処理中の印は90秒で無効）／次の定期実行待ち（自分の工程の案件がある）／引き継ぎ中／承認待ち（社長の承認・確認待ち）／エラー・再試行待ち／予算待ち／画像待ち／仕事なし（仕事探しの理由つき）
- 社員ごとの記録（v2:staff）：今日の仕事の数・工程の数・仕事探しの数・完成品への貢献（その社員が工程を完成させた案件のうち納品まで届いた数）・やり直し・停止・費用。作業の履歴は出来事の記録から
- くまの一言メモ（2026-11-16 社長の指摘「両方ともくまの一言メモがおかしい。これじゃ投稿できない」）：説明文の切れ端（「この一台が変えます」等）をやめ、AIが1文・30字以内の一言を書き、コードで確かめる（体験談・人気・口コミ・便利/安心・データに無い数字や性能は不合格。漢字・カタカナの言葉は商品データにあるか、立ち位置の一般的な言葉だけ）。合わなければ理由を添えて1回だけ書き直し、それでも合わなければ役割に合った決まった一言。納品済みの完成品は、編集が仕事探しで書き直す（lib/production.js の memoStep・memoOk）。補足文も、文の切れ端・注意書き・色名だけの言葉は使わない

## 16. OpenAIの残高不足（社長の依頼 2026-11-17）
- 残高不足（429 insufficient_quota・no credits remaining など）は、通常の失敗と分けて「残高待ち」（v2:cases の wait.kind = quota）にする。失敗の回数・画像の描き直しの回数に数えず、案件は終わらせない
- 残高待ちの間（v2:quota の until まで）は、AIを使う工程・仕事探し・新しい案件を始めない（AIを使わない工程と、広報の公式サイト調べ・完成品の楽天での再確認は続ける）
- until が来たら1件だけ試す（30分→1時間→2時間→4時間ごと）。AIが応答すれば残高待ちを解いて、残高待ちの案件をすべて続きから再開する
- 手動の実行（GitHub Actions の worker・workflow_dispatch）のときは、時刻を待たずにその場で1件だけ試す（チャージ直後にすぐ再開するため。2026-11-17）
- 前の実行で「再試行待ち」になっていた残高不足の案件は、失敗の回数を戻して残高待ちに移す（消さない）
- 広報のコメント案・採点、編集の一言メモの書き直しも、残高不足を失敗の回数に数えない
