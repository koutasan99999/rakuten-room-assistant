# バイヤー発掘便（商品バイヤー × 企画担当）

## コンセプト
「ランキングで見たことのある人気商品」ではなく、「こんな商品が存在するなんて知らなかった！」という発見を届ける。
対象：生活を豊かにするもの、時短につながるもの、便利なガジェット、日常の小さなストレスを解消するもの。

## 2つの便
| | アプリの便（画面の「発掘開始」） | Web調査便（Claude Code のサブエージェント） |
|---|---|---|
| 動かし方 | 「バイヤー発掘便」画面で「発掘開始」を押す（手動） | 社長が Claude Code に「バイヤー発掘便をWebで調べて」と頼む（手動） |
| バイヤー役 | アプリのサーバーのAI（OpenAI。既存のAPIキー） | `.claude/agents/product-buyer.md` |
| 企画担当役 | 同じAIの呼び出しで、企画担当として投稿案を作る | `.claude/agents/planning-lead.md` |
| 情報源 | 楽天市場の商品検索・総合ランキング | Web検索（メーカー公式・新製品情報・専門メディア・楽天市場） |
| 公式URL | 楽天の公式ショップのときだけ。ほかは「未取得」と表示 | 検索で実際に確認したURLだけ |
| 楽天にない商品 | 扱えない | 扱える（購入先と楽天ROOMに載せられるかを分けて表示） |
| 保存先 | このiPhone（`js/buyer-store.js`） | `data/buyer-picks.json`（リポジトリ。CEO補佐が保存） |

- アプリのサーバーから Claude Code のサブエージェントは呼べない。そのため、アプリの便は同じ役割を既存のAI（OpenAI）で行い、Web調査便は Claude Code のセッションで行う。
- どちらも自動では動かない（常時の自動実行は後回し）。

## 評価基準（社長の方針 2026-10-30 改訂。前の「厳しめ」の基準は廃止）
改訂の理由：知名度が高い・似た商品がある・ランキング上位、というだけで不合格にすると、紹介する価値のある商品を逃すため。

1. 商品の3つの種類（どれかに分ける）
   (1) 発掘商品：あまり知られていない、新しい仕組みや発想がある商品。珍しさそのものが紹介の理由になる。
   (2) 実績商品：知名度が高い、ランキング上位、レビューが多いなど、世の中での評判がある商品。特定の悩みを解決する、価格に納得感がある、などの紹介の理由がはっきりしていれば採用候補にする。「実績」は出典のある世の中の評判のことで、眼科医くまでの売上のことではない。
   (3) 比較商品：似た商品が複数ある種類。即不合格にせず、2〜4品を仕様で比べる「比較企画」として成り立つかで評価する。
2. 必ず通す審査（従来どおり厳格。1つでも満たさなければ不採用）
   (1) 安全性：リコール・回収の情報がないか。電気用品など、表示が必要な商品は表示を確認できるか（確認できなければ「未確認」として採用を保留）。
   (2) 事実確認：商品名・仕様・価格は、出典URLで確認できた値だけを使う。
   (3) 広告表示：PR表記を入れられる。体験していないことを書かない。医療・健康の効果をうたわない。医薬品・医療機器・メガネなど、眼科医の推薦と受け取られる商品は扱わない。
   (4) 権利関係：他人の画像・動画・文章・表紙タイトルを使わない。商品情報は自分で調べ直す。
3. 点数（各1〜5）
   (1) 紹介する理由の明確さ：特定の悩みを解決する／比べる価値がある／価格に納得感がある、のどれかがはっきりしているか
   (2) 実用性：日常で使う場面があるか
   (3) 欲しくなる魅力：見た人が欲しくなるか
   (4) 楽天ROOMへのつなぎやすさ：楽天市場の商品ページで買えるか（確認できた＝5、店はあるが商品ページ未確認＝3、楽天に無い＝1）
   (5) 珍しさ（加点）：必須ではない。発掘商品のときは高くなる
4. 採用候補の条件
   (1) 2の審査をすべて通る。
   (2) 紹介する理由の明確さが4以上、実用性が3以上、欲しくなる魅力が3以上。
   (3) 比較商品は、比べる相手の商品（2品以上）と、比べる項目が出典で確認できること。
   (4) 楽天ROOMへのつなぎやすさが1（楽天に無い）でも採用候補にできるが、「ROOMでは購入につなげられない」と明記する。
   (5) 数合わせはしない。採用候補が0件でもよい。見送った商品も理由を記録する。
5. 採用候補に必ず書くこと
   (1) 誰が、なぜ欲しくなるか
   (2) 楽天ROOMで購入につなげられるか（楽天の商品URLの確認状態）
   (3) 投稿でどう魅力を伝えるか（企画責任者へのつなぎ）
6. 評価と、売れるかの検証は分ける
   (1) バイヤーの評価は「紹介する価値がある」という判断で、「売れる」という意味ではない。売上の実績がないうちは「売れる商品」と書かない。
   (2) 売れるかどうかは、投稿した後の数字（保存・送信・プロフィールへのアクセス・楽天ROOMのクリック数とオーダー数）で確かめ、記録する。
7. 競合発見（経路B）の扱い
   (1) 別のSNS（TikTokなど）で紹介されていたことは「別のSNSでの紹介事例」と書く。Instagramでの成功の実績として扱わない。
   (2) Instagramの投稿で確認できたときだけ「Instagramで紹介されていた」と書く。数字は出典と時点つきでのみ書く。

## 発掘スコア（100点・第1便までの方式）
- AIの評価（70点）：意外性 45％・不便の解決 35％・日常での使いやすさ 20％（各1〜5）
- データ（30点、アプリの便）：楽天の総合ランキング上位に入っていない＝10点、レビュー件数が少ない（300件未満）＝20点・300〜3000件＝10点
- 知名度はレビュー件数とランキングからの「目安」。知られていないと断定しない。

## 評価と次の発掘への反映
- 「欲しい」「知ってる」「興味なし」「投稿にする」は、このiPhoneに保存する。
- 次の発掘での使い方：
  - 「知ってる」「興味なし」「投稿にした」商品と、投稿管理・投稿履歴にある紹介済みの商品は出さない。
  - 「知ってる」「興味なし」が多い種類は避ける。
  - 「欲しい」と言った種類の近くを探す。
- 「投稿にする」を押したときだけ、商品と企画担当の案（選んだタイトル・刺さる人・解決する不便・紹介文）を、今までの企画の画面に渡す（起点の商品として必ず採用。紹介文はROOM紹介文のたたき台になる）。

## Web調査便の進め方（CEO補佐）
0. 社長の評価：画面の「Web調査便」の「評価を書き出す」でコピーしたものを社長が Claude Code に貼ったら、docs/ai-team/buyer-feedback.json に保存して、バイヤーに「避ける商品・種類」として渡す。
1. product-buyer に、テーマと「避ける商品」（data/buyer-picks.json の既存の商品、社長から聞いた「知ってる」の商品）を渡す。
2. バイヤーの報告（商品・URL・スコア・理由）を、planning-lead に渡して投稿案を作らせる。
3. 監査責任者（audit-lead）が、出典にない言葉・言い過ぎ・規約の点を確かめ、商品ごとに「可／条件つき可／見送り」を付ける（見送りの商品は画面で「投稿にする」を押せない）。
4. CEO補佐が、URLが実在の検索結果にもとづくかを確かめてから data/buyer-picks.json に保存する（URLや価格を足さない）。

## Web調査便の発掘スコア
- AIの評価（意外性・不便の解決・日常での使いやすさ）だけで100点に換算する。アプリの便（AI70点＋データ30点）とは比べられないので、画面にそう書く。
- 知名度の目安は「新製品（発売日）」「クラウドファンディング」など分かる事実だけにして、知られていないとは書かない。

## 発掘の経路と、競合調査との連携（社長の方針 2026-10-30）
1. 経路A 独自発掘：メーカー公式・新製品のプレスリリース・専門メディアから探す（今までのWeb調査便）。
2. 経路B 競合発見：人気のガジェット・便利グッズ紹介アカウントが実際に紹介した商品から探す。
   (1) 材料は、競合調査担当の記録（docs/ai-team/competitors/）だけ。投稿URLを確認できた商品に限る。
   (2) バイヤーは公式情報を自分で調べ直し、眼科医くま独自の選定理由と、競合の紹介と違う切り口を書く。
   (3) 競合で反応があったことは「需要の手がかり」として書くが、点数には足さない（評価基準は経路Aと同じ）。別のSNSの事例は、Instagramでの実績として扱わない。
   (4) 競合の画像・動画・文章・表紙タイトルは使わない。発見元の投稿URLは社内の記録だけに残し、投稿には書かない。
3. 課題先行：企画責任者が「誰の、どんな場面の、どんな不便」の依頼書を出したときは、経路A・Bのどちらでも、それに合う商品を優先して探す。
4. data/buyer-picks.json に足す項目（設計案。アプリの画面の変更は、次に必要になったときに小さく行う）
   (1) route：「A」か「B」
   (2) foundVia：経路Bのときの発見元（アカウント名・投稿URL・確認した日）
   (3) angle：競合の紹介と何を変えるか
   (4) brief：課題先行の依頼書から探したときの、依頼書の名前
