# サングラスくま株式会社 2.0 基本設計（2026-11-15）

社長の指示（2026-11-15）を新しい基本設計として扱う。過去の細かな仕様は無条件には引き継がない。
動作を確認してきたAPI接続・費用管理・定期実行・投稿制作の処理は再利用する。
この文書の段階では、本番・既存データ・旧アプリには一切触れない。

---

## 0. 結論

1. 「AI社員がオフィスで働き、引き継ぎながら投稿セットを完成させる」を、**仕事（Job）と出来事（Event）の2つの記録だけ**で作る。オフィス画面・仕事の流れ・完成品は、すべてこの記録から描く（演出だけの動きは作らない）。
2. 旧アプリ（眼科医くま）はそのまま本番で動かし続ける。2.0 は同じリポジトリ・同じVercelのプロジェクトの中に **別の入口（/v2/）と別の保存場所の名前（v2:）** で作る。切り替えは、2.0 で投稿セットが本番で完成したことを社長が確認してから。
3. 仕事の流れは一本道に絞る：**発掘 → 監査 → 企画 → 文章 → 画像 → 仕上げ確認 → 社長へ納品**。承認は「外に出すとき（Instagram・ROOMへの公開、コメント）」だけ。社内の工程に社長の承認待ちは置かない。

## 2. 2.0 の全体の形

```
iPhone（/v2/ ・1画面＋下から出る詳細）
   └─ GET /api/v2?action=office｜timeline｜deliveries｜costs   （読むだけ）
   └─ POST /api/v2  decide（採用・却下・修正依頼）｜pause｜resume
QStash（15分ごと）→ /api/v2?action=tick → lib/v2/engine.js（仕事を1段階だけ進める）
                                           └─ 社員ごとの仕事（lib/v2/roles/*.js）→ 既存の lib を呼ぶ
保存場所（同じ Upstash・鍵は v2: で始める）
```
- Vercel Hobby の関数の数：api/[route].js の振り分けに v2 を1つ足すだけ（関数は増えない）。
- 旧アプリの定期実行（/api/worker）と2.0の定期実行（/api/v2）は、どちらか一方だけを動かす。開発中は 2.0 を「手動の1段階実行」とPreviewだけで動かし、本番の QStash は旧アプリのまま。切り替え時に QStash の宛先を変える（元に戻せる）。

### 2-1. 記録の形（これだけ）
**Job（仕事）** `v2:job:{id}`
```
{ id, product: 'post_set', status: 'running'|'waiting'|'blocked'|'done'|'failed',
  stage: 'discover'|'audit'|'plan'|'write'|'image'|'final'|'deliver',
  owner: 社員ID, input: {...}, output: {...}, createdAt, updatedAt, blockedReason? }
```
**Event（出来事）** `v2:events`（新しい順・保存は最大2,000件、それより古いものは日別の保管へ移す。消さない）
```
{ at, jobId, agent, type: 'start'|'done'|'handoff'|'blocked'|'resume'|'deliver'|'decide',
  text: '社長向けの1行', to?: 次の社員, artifact?: { kind, ref }, dev?: { 段階・費用・応答ID・点数 } }
```
- 社長の画面は text・agent・to・artifact だけを使う。点数・費用の内訳・応答ID は dev に入れ、開発者向けの記録でだけ見る。
- Event はエンジンが実際に処理した直後にだけ書く（画面側で作らない）。だから「架空の作業履歴」は構造上できない。
- 事業が増えたとき（note出版・デジタル商品）は、Job の product を増やし、その工程表（stage の並び）と各段階を担当する社員を定義するだけ。社員・記録・画面はそのまま使う。

### 2-2. 社員（7人）と担当
| 社員 | 担当する段階 | 中身（再利用） |
|---|---|---|
| バイヤーAI | discover：楽天で候補を探す（基本の検索だけ） | lib/agents.js の候補選び |
| 監査AI | audit：候補の確認／final：完成品の仕上げ確認 | lib/agents.js の監査・lib/production.js の codeCheck と監査 |
| 企画AI | plan：投稿の構成と商品の組み合わせ | planStep・gatherStep・pickStep |
| 文章AI | write：表紙の文字・商品カード・キャプション・ROOM紹介文・ハッシュタグ | copyStep・roomStep・factCard |
| 画像AI | image：サングラスくまの表紙画像 | lib/kuma-cover.js |
| 修正AI | final で直しが必要なとき、指示どおりに直す（2回まで） | editStep・applyEdit |
| 広報AI | 完成品の公開の準備（Instagram用の文面・ROOMを開くリンク）と、コメント案。送信はしない | lib/outreach.js（案まで）・lib/comment-log.js（記録） |
社長の席：社長の判断（採用・却下・修正依頼）が要るものだけが届く。

### 2-3. 仕事の流れのルール（止まらないための最小限）
1. 1回の定期実行で、1つの Job を1段階だけ進める（60秒以内）。
2. 優先順位は1つだけ：**完成に近い Job から進める**（final → image → write → plan → audit → discover）。新しい発掘は、進行中の Job が無いか、すべて待ち（予算・画像の上限）のときだけ。
3. 予算：仕事を始める前に「その段階の見込み（実測から）」だけを確かめる。完成に近い Job のために、制作1件分を取り置く（11/15 の仕組みをそのまま使う）。1日25円・月1,000円は変えない。
4. 社長の承認待ちで止めない：納品（deliver）した Job は社長の判断を待つだけで、ほかの社員は次の Job を進める。納品待ちが3件たまったら、新しい発掘だけを止める（費用を見られないものに使わない）。
5. 止まったとき：Job を blocked にし、理由を1行（例「今日の予算の残り1.2円・画像の見込み20円。明日0:00に再開」）で Event に書く。同じ理由で3回止まったら、その Job を failed にして次へ（無限に待たない）。
6. 画像が作れない（上限・失敗）ときは「画像なし」で納品しない。完成品＝画像と文章がそろったもの。画像だけ翌日に回す。

## 3. 社長の画面（iPhone縦・1画面）

上から順に：
1. **オフィス**（見下ろし型の2Dドット絵・7つの机＋会議スペース＋社長の席）
   - 社員の位置と動きは Job の状態から決める：仕事中＝自分の机でパソコンに向かう／引き継ぎ＝次の社員の机へ書類を持って移動（Event の handoff が来たときだけ）／待機＝休憩スペース／止まっている＝机に「！」
   - 社員をタップ → 下から詳細：今の仕事（1行）・直近の成果（最大3件、完成品へのリンク）
   - 描画は canvas（ドット絵の素材は自作のSVG/PNGをリポジトリに置く。外部の素材・既存のキャラクターは使わない）
2. **仕事の流れ**（今日の Event を時刻順に1行ずつ）：「10:00 バイヤーAIが商品を発掘」「10:03 監査AIへ引き継ぎ」…。止まった行は理由つきで目立たせる
3. **完成した投稿セット**：商品（名前・価格・楽天のURL）・完成した紹介文（キャプション・ROOM紹介文）・完成した画像。ボタンは「採用」「却下」「修正依頼（一言）」だけ
4. **社長がやること**：判断待ちの件数、鍵の設定などの本当に必要な依頼だけ
5. **お金**：今日・今月のAIの実費（実測）と売上（社長の入力・未入力は「未入力」）

出さないもの：監査の点数・採点理由・長い記録・同期の問題・技術的な警告（開発者向けの記録 /v2/#dev にだけ）。

## 4. 過去データ

- 引き継がない：未投稿の候補・承認待ち・古い投稿セット・同期の問題（2.0 は空から始める）。
- 保管する（消さない）：旧アプリのデータは本番の保存場所にそのまま残す（旧アプリも動いたまま）。切り替えの前に、/api/data の export（既存）でサーバーの全件を書き出し、社長の端末の全件はアプリの「バックアップ」（js/backup.js saveFull）で保存する。投稿済みの記録・費用の記録・コメントの送信記録は 2.0 の画面からも読めるようにする（読むだけ）。
- 削除はしない。旧データの整理は、切り替えて1か月たってから社長に確認する。

## 6. 実装の段階と完成判定

| 段階 | 内容 | 完成判定 |
|---|---|---|
| A 土台 | lib/v2/engine.js（Job・Event・優先順位・予算・止まったときの扱い）・/api/v2・テスト | テストで、1つの Job が7人を通って納品まで進み、Event が全段階で残る。予算不足・失敗で blocked になり理由が残る |
| B 社員 | 各段階を既存の lib につなぐ（基本の検索だけ） | Preview の保存場所（v2:）で、手動の1段階実行をくり返し、実際のAI・楽天・画像生成で投稿セットが1件納品される |
| C 画面 | /v2/ のオフィス・仕事の流れ・完成品・社長がやること・お金 | Playwright（iPhone 13）で、B の実データが画面に出る。社員をタップして今の仕事と成果が見える |
| D 本番での確認 | 本番の /v2/ を手動実行で1件完成させる（旧アプリはそのまま） | 本番で画像と文章を含む投稿セットが1件完成し、流れがオフィス画面で確認できる |
| E 切り替え | 社長の確認後、QStash の宛先を /api/v2 に変え、トップを 2.0 にする。旧アプリは /legacy/ で読めるまま | 切り替え後の1日で、定期実行だけで1件以上納品される |

- 費用：開発中のAIの呼び出しは、今と同じ予算の上限の中（増額しない）。新しい有料サービスは使わない。
- 旧アプリとの共存中は、2.0 の定期実行を動かさない（同じ1日25円を取り合わないため）。D の本番確認は手動の1段階実行で行う。
