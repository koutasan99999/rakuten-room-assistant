## 0. 結論（推奨案）

1. いちばん大きな障害は「公開」と「効果測定」の工程が会社の中で一度も完結していないこと。商品選定・制作・監査はサーバーで自動で回るが、成果物は社長のiPhoneの中で止まり、Instagramにも楽天ROOMにも出ていかない。出ていかない以上、売上は発生しない。
2. 最初の実装は「投稿セットと社長の判断の正本をサーバーに移し、承認待ちで会社が止まらない形にする」こと（段階1）。公開の自動化（段階2）と効果測定（段階3）は、この正本の上に作る。
3. 既存の機能を足すのではなく、使っていない旧機能は削除候補として整理し、社長の確認とデータの書き出しのあとで消す。

## 3. 社長の承認待ち・固定の上限で止まる構造の見直し

【事実】11/14 09:16 の仕事探しの記録：制作は「確認待ちの投稿セットが6件」で待ち、バイヤーAIは「合格候補が4件」で待ち、営業・交流AIは材料が無く待ち → 会社全体が停止。

見直し（品質・安全・予算の制御は残す）：
1. 承認は「外部に出すとき」だけにする（Instagramへの公開・ROOM登録の案内・コメント送信・フォロー）。社内の工程（選定・制作・監査・修正）は承認なしで進む【今もこの方針。維持】。
2. 「確認待ち6件で制作を止める」をやめ、確認待ちの棚を2段にする：
   - 公開待ち（上位3件）：社長に見せるのはここだけ。監査の点数・新しさ・商品の重複の少なさで並べる
   - 控え（それ以外）：消さずに保管。14日たったものは「期限切れ」に移す（消さない）。公開待ちが空けば控えから自動で繰り上げる
   制作の上限は「確認待ちの件数」ではなく「1日の件数（3件）と費用の上限」で決める。
3. バイヤーAIの「合格候補4件で待ち」は残す（制作が追いつかない候補を増やしても費用だけかかるため）。
4. 社長が見ていない状態が続く（7日間判断が無い）ときは、制作を1日1件に落とし、経営報告のいちばん上に「公開待ちが止まっている」と出す（費用をかけ続けない）。

## 4. サーバーを正本にする構造と、データを失わない移行

### 4-1. 保存の形（Upstash Redis・無料枠 256MB）
| キー | 中身 |
|---|---|
| data:set:{id} | 投稿セット1件（商品・文章・監査・状態：draft／shelf／ready／approved／published／rejected／expired・社長の判断と理由・公開記録） |
| data:sets:index | 投稿セットのIDと状態・作成日時の一覧（並べ替え用） |
| data:roomtext:{商品番号} | ROOM紹介文とハッシュタグ・ROOM登録（社長の申告） |
| data:revenue:{YYYY-MM} | 発生報酬・確定報酬（社長の入力・CSV） |
| data:perf:{投稿ID} | 投稿ごとの指標（公式API・手入力。未取得は null） |
| data:migrate:{端末ID} | 移行の記録（いつ・何件・照合の結果） |
1件ずつ別のキーにする（1回の要求が大きくなりすぎないように。Upstash の1要求の上限は未確認）。

### 4-2. 移行（既存データを消さない）
1. アプリが「バックアップ（js/backup.js の collect）」と同じ中身を、1件ずつ /api/data に送る（合言葉が必要）。
2. サーバーは ID で上書きせずに取り込む（同じIDがあれば、更新日時が新しい方だけ）。
3. 取り込み後、サーバーから読み戻して件数とIDを照合し、一致したら「移行済み」と記録する。
4. iPhone の localStorage は消さない（読み取り専用の控えとして残す）。移行後は、画面はサーバーから読み、書き込みもサーバーへ送る。サーバーに届かないときは今までどおり端末に書き、次に届いたときに送る。
5. 失敗しても何も消えない。何度やり直しても同じ結果になる（冪等）。

## 5. 最初の実装（段階1）：投稿セットの正本をサーバーへ移し、承認待ちで止まらない形にする

### 5-1. 実装するファイル
| ファイル | 内容 |
|---|---|
| lib/store.js（新規） | サーバーの正本の読み書き（data:*）。状態の遷移のルール（draft→shelf／ready→approved→published、rejected、expired）。棚の並べ替えと繰り上げ |
| server/data.js（新規）＋ api/[route].js | /api/data：import（移行）・list・get・decide（採用・却下・理由）・verify（読み戻しの照合）。合言葉が必要 |
| lib/worker.js | 制作ラインの合格品を data:set に保存（今は worker:results:production → アプリの localStorage）。「確認待ち6件で止める」を3章の棚の仕組みに置き換え。期限切れ・繰り上げを定期実行で行う |
| js/server-sync.js・js/delivery-store.js | 移行（1件ずつ送る・照合）。投稿セットの読み書きをサーバー経由に（届かないときは端末に書いて後で送る） |
| js/delivery.js・js/work.js | 公開待ち（上位3件）と控えの表示。判断はサーバーへ |
| PROJECT_STATUS.md・CLAUDE.md | 保存場所の説明を「サーバーが正本」に更新 |

### 5-2. テスト（npm test・node:test）
1. 移行：localStorage の投稿セット（旧形式を含む）をすべて取り込み、読み戻しで件数・IDが一致する。2回送っても増えない。サーバーの新しい判断を古い端末のデータで上書きしない。
2. 状態の遷移：許されない遷移（例：rejected→published）を拒否する。公開は approved からだけ。
3. 棚：公開待ちは3件まで。控えから点数順に繰り上がる。14日で期限切れに移す（消さない）。
4. 停止しない：確認待ちが何件あっても、1日の件数と費用の上限の範囲で制作が進む。7日間判断が無ければ1日1件に落ちる。
5. 画面（Playwright・iPhone 13・MOCK）：移行の前後で投稿セットの件数と中身が同じ。採用・却下がサーバーに残り、別の端末（新しいブラウザ）でも同じに見える。

### 5-3. 完成判定
- 本番の既存の投稿セットがすべてサーバーに移り、件数・IDの照合が一致した記録がある（iPhoneのデータは消えていない）
- 確認待ちが上限を超えても、仕事探しの記録で制作が「待ち」にならず、控えに入る
- 社長が採用・却下した結果が、サーバーの正本に残る
- 既存のテストがすべて通る
