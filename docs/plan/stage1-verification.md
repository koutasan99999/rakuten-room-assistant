## 2. 本番での確認（承認のあと）
1. PR #91 を取り込み、Vercel のデプロイが success になったことを確かめる
2. 社長がiPhoneでアプリを開く → 移行（10件ずつ取り込み→中身・判断・件数の照合）
3. 確かめること（手動の実行の応答・画面）
   - 移行：照合で全件一致（room-data-sync の migratedAt）。差異があれば「同期の問題」に出て、端末の中身は残っている
   - サーバー：公開待ち3件以下・控え6件以下・件数の合計が端末の投稿セットの数と同じ
   - 定期実行（QStash）：仕事探しの記録に「確認待ちが満杯」なら点検・効果測定・公開の準備へ移る理由が出る
   - 別の端末（パソコンのブラウザ）で開いて、同じ投稿セットと状態が見える
4. 問題があったとき（ロールバック）：「コードを戻すこと」と「データを元に戻すこと」は別の作業
   - コードを戻す：PR #91 の取り込みを取り消す（revert）。これで画面とサーバーの動きは今まで（端末の記録だけ）に戻る。ただし、サーバーに書かれた data:* の鍵は消えずに残り、端末の room-delivery に足された印（_server・outbox・conflicts）や room-data-sync も残る（今までのコードは、これらを読まないので動きには影響しない）
   - データを元に戻す：コードを戻しても、データは自動では戻らない。必要なときだけ、次の順で行う
     1. まず、今の端末とサーバーのデータを、もう一度書き出して保存する（戻す前の状態も失わない）
     2. 端末：移行前のバックアップのファイルから room-delivery を戻す（ほかのキーは触らない）。注意：アプリには今、バックアップを読み込んで戻す機能が無い（書き出しだけ）。必要になったときは、戻す手順（room-delivery だけを書き戻し、戻す前の内容を別に保存する）を用意し、社長の承認をとってから行う
     3. サーバー：data:* の鍵は消さずに残しておく（後で調べるため）。消すときは社長の確認をとる
   - 戻したあとの確認項目
     - 端末の投稿セットの件数が、移行前のメモと同じか（却下・採用を含む）
     - 採用・却下・確認待ちの状態が、移行前と同じか（数件を開いて中身を見る）
     - 「同期の問題」に残っていた端末の中身・判断を、戻す前に書き出したか
     - 定期実行（QStash）の記録で、エラーが続いていないか
